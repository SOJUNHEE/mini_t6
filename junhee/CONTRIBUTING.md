# AXPORT 협업 규칙

- 작성일: 2026-09-22
- 버전: 0.1
- 상태: 팀 채택용 초안
- 배치 위치: 저장소 최상위 `CONTRIBUTING.md`
- 목적: 각자의 개발 환경에서 작업한 변경을 Pull Request(PR)로 검토하고 안전하게 병합한다.

이 문서는 제안하는 팀 공통 규칙이다. 팀에서 채택한 뒤 모든 기여에 적용한다. Python·Node 버전, 패키지 관리자, CI 명령, 리뷰 담당자는 실제 기술 스택을 결정한 후 채운다. 문서만 추가한다고 GitHub의 브랜치 보호나 CI가 설정되지는 않는다.

## 1. 개발 시작 전에 팀이 확정할 사항

| 항목 | 제안 또는 기록할 값 |
|---|---|
| 기본 브랜치 | `main` |
| 병합 방식 | Squash merge |
| 최소 리뷰 | 작성자 외 1명 승인 |
| Python 버전 | 선정 후 `.python-version`과 README에 동일하게 기록 |
| 프런트엔드 런타임 | Node 사용 시 버전 파일과 README에 기록 |
| Python 의존성 관리 | 프로젝트 전체에서 한 가지 방식 선택 |
| 프런트엔드 패키지 관리자 | 사용 시 npm·pnpm·yarn 중 하나 선택 |
| 필수 CI | 채택한 린트·테스트·빌드 명령 및 체크 이름 |
| 리뷰 담당 | 기능·데이터·판정 규칙별 담당자 |
| 데이터 공유 위치 | 대용량·비공개 자료의 별도 저장소 또는 공유 경로 |
| 데이터 보관·삭제 | 실제 기업 자료를 받기 전에 확정 |

## 2. 작업 시작과 범위 공유

- 작업 전 README, 초기 개발 명세, 관련 디자인·데이터 문서, 이 문서를 읽는다.
- 기능·수정 작업은 이슈나 팀 작업 목록에 목적, 범위, 담당자를 기록한다.
- 같은 파일을 여러 사람이 수정할 가능성이 있으면 먼저 조율한다.
- API 응답, 엑셀 컬럼, 데이터베이스, 공통 스타일, 판정 규칙 변경은 영향을 받는 담당자와 먼저 공유한다.
- 한 PR은 하나의 목적을 갖도록 한다. 무관한 리팩터링·전체 포맷 변경을 섞지 않는다.
- 남아 있는 로컬 변경은 먼저 확인한다. 작업을 시작한다는 이유로 다른 작업을 삭제하거나 덮어쓰지 않는다.

## 3. 파일·폴더 이름과 문자 규칙

### 기본 규칙

- 새 코드·설정·폴더 이름은 영문 소문자 중심으로 작성하고 공백을 사용하지 않는다.
- 폴더·일반 문서: `kebab-case` — 예: `export-control/`, `data-catalog.md`.
- Python 모듈·함수·변수: `snake_case` — 예: `tariff_service.py`.
- React를 채택할 경우 컴포넌트 파일: `PascalCase.tsx` — 예: `AnalysisWindow.tsx`.
- 기타 JS/TS 파일: `kebab-case` — 예: `api-client.ts`.
- 환경변수: `UPPER_SNAKE_CASE` — 예: `ECOS_API_KEY`.
- `README.md`, `CONTRIBUTING.md` 등 관례적인 파일명과 현재 합의된 기획 문서 이름은 예외로 둔다.
- 공식 원본자료는 한글 원본 파일명을 유지해도 된다. 내부 데이터 ID와 저장 경로 규칙은 별도로 관리한다.
- 대소문자만 다른 파일을 만들지 않는다. Windows·macOS·Linux에서 같은 경로로 접근할 수 있어야 한다.
- `final`, `final2`, `진짜최종`, 개인 이름으로 버전을 관리하지 않는다. 코드 변경은 Git, 외부 자료는 명시적인 버전 폴더로 관리한다.
- 파일의 실제 형식과 확장자를 일치시킨다.

### 텍스트·경로

- 코드·설정·Markdown은 UTF-8, 줄바꿈은 LF를 기본으로 한다. 원본 HWP·PDF·XLSX 등은 변환하지 않는다.
- Python은 공백 4칸, 프런트엔드는 채택한 포매터를 따른다. 팀 공통 `.editorconfig`와 포매터 설정으로 고정한다.
- `.gitattributes`에서 텍스트 줄바꿈과 바이너리 파일 처리를 명시한다.
- 개인 PC 절대경로, 사용자명, 바탕화면 경로를 코드·설정에 하드코딩하지 않는다.
- 경로는 프로젝트 기준 상대경로 또는 환경설정으로 해석한다. Python에서는 `pathlib` 등을 사용한다.
- 대소문자만 변경할 때는 중간 이름을 거쳐 Git이 변경을 인식하게 하고 PR에서 확인한다.

## 4. 가상환경·런타임

- 저장소마다 각자 가상환경을 만든다. Python 가상환경 이름은 프로젝트 루트의 `.venv`로 통일한다.
- 다른 사람의 `.venv`를 복사하거나 Git에 올리지 않는다.
- VS Code 인터프리터도 해당 프로젝트 `.venv`로 선택한다.
- `.venv`, `node_modules`, 캐시, 빌드 산출물은 공유하지 않고 의존성 명세에서 재생성한다.
- Python·Node 버전은 팀 지정 버전에 맞춘다. 개인 판단으로 올리지 않는다.
- 전역 설치 패키지나 개인 컴퓨터에만 있는 프로그램에 실행을 의존하지 않는다.
- 외부 실행 파일이 필요하면 이름·설치법·지원 환경을 README에 기록한다.

Python 가상환경 생성 예시(먼저 지정 Python 버전을 확인):

```powershell
# Windows PowerShell, 저장소 루트에서 실행
python --version
python -m venv .venv
.\.venv\Scripts\python.exe -m pip --version
```

```bash
# macOS / Linux, 저장소 루트에서 실행
python3 --version
python3 -m venv .venv
.venv/bin/python -m pip --version
```

가상환경 활성화는 선택 사항이다. 위처럼 가상환경의 Python을 직접 지정하면 시스템 Python과 혼동을 줄일 수 있다. 의존성 설치·앱 실행 명령은 선택한 도구에 맞춰 README를 따른다.

## 5. 의존성 변경

- 프로젝트의 의존성 관리 방식을 임의로 혼용하지 않는다.
- 패키지 추가·삭제·버전 변경 시 소스 명세와 잠금 파일을 함께 변경한다. 사용하는 방식에 잠금 파일이 없다면 재현 가능한 버전 관리 절차를 정한다.
- 로컬에 패키지만 설치하고 PR에서 의존성 파일을 빠뜨리지 않는다.
- 프런트엔드 패키지 관리자는 하나만 사용하고 잠금 파일도 그 도구의 파일만 유지한다.
- 관련 없는 개발 도구가 섞인 개인 환경의 `pip freeze` 결과로 공통 의존성을 덮어쓰지 않는다.
- 의존성 변경 이유·실행 환경 영향·검증 결과를 PR에 적는다.
- 잠금 파일 충돌은 내용을 임의로 조합하지 말고 소스 명세를 정리한 뒤 해당 관리자로 재생성하고 검증한다.
- 변경된 의존성은 깨끗한 환경 또는 CI에서 설치 가능한지 확인한다.

## 6. API 키·환경변수

- 실제 키는 로컬 `.env` 또는 운영·CI의 비밀값 저장소에서 관리한다.
- `.env.example`에는 공통 변수명·설명·빈 값 또는 비밀이 아닌 예시만 넣는다.
- 키를 코드, Markdown, 샘플 데이터, 캡처, PR 본문, 로그에 넣지 않는다.
- 서버 키를 프런트엔드 번들에 포함하지 않는다. `VITE_`, `NEXT_PUBLIC_`처럼 공개되는 변수 접두사에 비밀값을 넣지 않는다.
- 환경변수를 추가·변경하면 `.env.example`, 설정 검증, README를 함께 수정한다.
- 개발·테스트·운영 환경을 구분하고 테스트는 기본적으로 실제 외부 API를 호출하지 않는다.
- 실서비스 호출 검증은 별도로 실행하고 사용 범위·요금·호출 제한을 확인한다.
- 키가 노출되면 파일에서 지우는 것으로 끝내지 않는다. 즉시 담당자에게 알리고 폐기·재발급하며 Git 이력 정리를 조율한다.

## 7. 데이터·파일 관리

### 저장 위치

```text
data/
  reference/
    raw/          # 공식 외부 원본, 버전별 보관
    processed/    # 추출·정규화 결과
  samples/        # 가상 기업 데이터
rules/            # 검토된 판정 규칙
instance/
  uploads/        # 실제 기업 업로드, Git 제외
  reports/        # 생성 보고서, Git 제외
  cache/          # API 캐시, Git 제외
```

- `raw/` 원본은 직접 수정하지 않는다. 새 자료는 새 버전 폴더에 추가한다.
- 출처·기준일·시행일·수집일·버전·해시·이용조건을 manifest 또는 자료 목록에 기록한다.
- 실제 기업 자료·개인정보·비공개 문서는 Git에 넣지 않는다. 테스트에는 가상 또는 검증된 비식별 자료를 사용한다.
- 공개된 파일이라고 자동으로 Git에 올리지 않는다. 이용·재배포 조건과 크기를 확인한다.
- 대용량 원본은 합의된 외부 저장 위치에 두고 목록·해시·복원 방법을 버전 관리한다. Git LFS는 팀 합의 시 사용한다.
- 자동 생성된 `processed/` 파일을 커밋할지 정하고, 가능하면 변환 스크립트와 입력 버전으로 재생성한다.
- 실제 자료·샘플·가정값을 섞지 않는다. API 실패 시 샘플 자료로 조용히 대체하지 않는다.
- HWP·PDF의 추출 결과는 원문 표·주석과 대조한다. 미검토 내용을 확정 판정 규칙으로 등록하지 않는다.

실제 저장소 구조에 맞게 `.gitignore`에 반영한다. 폴더 자체를 만들었다고 자동으로 제외되지는 않는다.

# 빌드·테스트 산출물

## 8. 브랜치·커밋

- `main`은 리뷰와 검증을 거친 상태를 유지한다. 직접 push하지 않는다.
- 작업마다 최신 `main`에서 짧은 작업 브랜치를 만든다.
- 브랜치 이름: `feat/<issue>-<topic>`, `fix/<issue>-<topic>`, `docs/<topic>`, `chore/<topic>`.
- 예: `feat/12-upload-validation`, `fix/28-tab-focus`.
- 브랜치를 여러 사람이 함께 쓸 경우 이력을 바꾸는 rebase·강제 push를 하지 않는다.
- 브랜치 동기화는 기본적으로 `main`을 작업 브랜치에 merge한다. 개인 브랜치의 rebase는 협업 영향 확인 후 선택한다.
- `main`과 공유 브랜치에 강제 push하지 않는다. 개인 브랜치에서도 불가피한 경우에만 사전 공유 후 `--force-with-lease`를 사용한다.
- 커밋 메시지는 `feat: 엑셀 검증 추가`, `fix: 결측 환율 처리 수정`처럼 목적을 적는다.
- `수정`, `작업`, `최종` 같은 메시지는 피한다.
- 커밋 전 `git status`와 staged diff를 확인한다. `git add .`로 키·원본·생성파일이 섞이지 않게 한다.

기본 시작 예시:

```bash
git status
git switch main
git pull --ff-only origin main
git switch -c feat/12-upload-validation
```

로컬 변경이 있으면 위 흐름을 진행하기 전에 안전하게 보존한다. `pull --ff-only`가 실패하면 강제로 덮어쓰지 말고 분기 원인을 확인한다.

## 9. Pull Request 작성

- 작업 중 피드백이 필요하면 Draft PR을 연다.
- 제목은 변경의 목적을 설명하고 관련 이슈를 연결한다.
- PR 본문에는 문제·최종 동작·변경 범위·검증·영향을 적는다.
- UI 변경은 주요 상태와 작은 화면의 캡처를 첨부한다. 캡처에 키·기업 민감정보가 없도록 한다.
- API 변경은 요청·응답·오류·호환성 영향을 적는다.
- 데이터 구조·의존성·환경변수·설치 절차 변경은 문서도 함께 수정한다.
- 실행하지 않은 테스트를 통과했다고 쓰지 않는다.
- 미완료 사항이나 운영 전 필요한 작업을 숨기지 않는다.

### PR 본문 양식

```markdown
## 목적
- 해결할 문제와 변경 후 동작

## 주요 변경
- 구현 내용과 영향 범위

## 검증
- 실제 실행한 명령과 결과
- 미실행 항목과 이유
- UI 변경 시 캡처

## 호환성·운영 영향
- 환경변수·의존성·API·데이터 구조·규칙 변경 여부
- 마이그레이션·설정·재수집 필요 여부
- 되돌릴 때 필요한 조치

## 관련 작업
- 관련 이슈와 후속 작업
```

## 10. 리뷰·충돌 해결·병합

- 작성자 외 최소 1명의 리뷰 승인을 받는다.
- 판정 규칙·계산식·데이터 접근권한 변경은 해당 담당자의 검토를 포함한다.
- 필수 CI가 성공하고 미해결 리뷰가 처리된 뒤 병합한다.
- 승인 후 의미 있는 변경이 추가되면 재검토를 요청한다.
- 충돌은 양쪽 변경 의도를 확인하고 해결한다. `ours`·`theirs`로 전체를 무조건 덮어쓰지 않는다.
- 충돌을 해결하거나 관련 코드가 바뀌면 영향을 받는 검증을 다시 실행한다.
- 기본 병합 방식은 Squash merge로 통일하고 최종 제목·설명을 정리한다.
- 병합 완료 후 더 사용하지 않는 작업 브랜치를 삭제하고 로컬 `main`을 갱신한다.
- 병합은 배포와 구분한다. 자동 배포 여부·승인·롤백 정책은 따로 설정한다.
- 큰 변경은 이전 코드뿐 아니라 데이터·규칙 버전도 되돌릴 수 있는지 확인한다.

## 11. 프로젝트별 필수 검토 항목

### 데이터·판정

- 0, 미입력, 미평가, 해당 없음을 구분했는가?
- 필수 조건 미확인을 다른 점수로 상쇄하지 않는가?
- 계산 단위·통화·기간·HS 버전이 일치하는가?
- 새 규칙에 근거·시행일·버전·검토 상태가 있는가?
- 결과와 보고서가 같은 평가 실행을 사용하는가?
- 입력·규칙 변경이 과거 결과를 조용히 바꾸지 않는가?

### 화면

- 홈 시안과 앱 시안의 역할 및 공통 디자인 규칙을 따르는가?
- 책갈피 전환 시 기업·제품·국가·평가 맥락이 유지되는가?
- 로딩·빈 상태·오류·자료 부족을 구분하는가?
- 창을 줄이거나 화면 크기가 바뀌어도 조작부에 접근 가능한가?
- 번역 문구·단위·날짜·키보드 조작을 고려했는가?

### 보안·운영

- 서버에서 기업·사용자 소유권을 확인하는가?
- 키·민감정보가 코드·로그·캡처에 없는가?
- 외부 API 실패·시간 초과·호출 제한을 처리하는가?
- 원본 자료나 다른 사용자의 변경을 훼손하지 않는가?

## 12. 테스트·CI 원칙

- README에 누구나 같은 순서로 실행할 설치·개발·검증 명령을 제공한다.
- 채택한 명령을 CI에서도 사용하고 로컬과 CI의 런타임 버전을 맞춘다.
- PR 기본 검증은 비밀키 없이 재현 가능하게 한다. 외부 API 테스트는 분리한다.
- 일반 PR 검증에 실제 기업 자료·운영 데이터베이스·운영 키를 사용하지 않는다.
- 변경에 맞는 의미 있는 검증을 한다. 저위험 문구 수정에 불필요한 전체 테스트를 강제하지 않는다.
- 계산식·판정 규칙·권한·업로드 처리 변경에는 경계값·누락·거절 경로를 검증한다.
- 기존 실패가 발견되면 숨기지 말고 변경 원인인지 구분하여 기록한다.
- 구조·도구가 확정되기 전 존재하지 않는 테스트 명령을 필수 통과 명령처럼 기록하지 않는다.
